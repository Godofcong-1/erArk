# 静态检查系统设计文档

## 1. 目的与边界

游戏可能进入逻辑上不应出现、但暂时不会立刻崩溃的状态，例如互斥标记同时为真、场景名册与角色位置不一致、派生岗位集合滞后。静态检查系统在玩家回到主场景并等待下一次输入前，重新计算 288 条不变量；发现失败时把最近输入、最近行为和涉事状态快照追加到游戏进程工作目录下的 `static_check_error.log`。载入存档后，系统还会对十一类具有唯一保守答案的旧数据异常执行修复并逐条留痕。

本系统的首要保证是：**绝不抛异常，绝不阻断游戏。** 检查失败、单条检查实现异常、修复失败、日志写入失败都只能留下或丢失诊断信息，不能改变游戏主流程。

`Static_Check/` 是位置无关的运行时检查包，放在 `Script/Test/Static_Check/`（`Script/Test/` 收纳不含玩法的自检类功能）。游戏本体只在三处各加几行调用，检查逻辑全部留在本包内。

## 2. 模块布局与依赖

```text
游戏侧三处调用（各 3–5 行，见第 8 节）
  ├─ Script/Core/save_handle.py: input_load_save 末尾 ──► run_load_repair()
  ├─ Script/UI/Panel/in_scene_panel.py: askfor_all 之前 ──► run_turn_check()
  ├─ Script/UI/Panel/in_scene_panel_web.py: askfor_all 之前 ──► run_turn_check()
  └─ data/csv/System_Setting.csv: 系统设置 cid 14“是否开启游戏状态自检”，默认关闭
Script/Test/Static_Check/__init__.py
       ├─ check_registry.py ◄──── checks/*.py
       ├─ check_log.py ─────────► snapshot.py
       ├─ checks/__init__.py ───► 14 个显式静态导入
       └─ repair.py ────────────► Script/Design/basement.py（唯一反向依赖）
```

职责如下：

- `__init__.py`：唯一公开门面；读取全局 cache、做就绪守卫、调用框架实现并持有总兜底。
- `check_registry.py`：`CheckFailure`、检查注册表、`register_check` 与 `make_failure`。
- `checks/*.py`：288 条只读检查。每个模块由 `checks/__init__.py` 独立 `try/except` 导入；一个模块导入失败不会阻止后续模块注册。必须保留显式 import，供 PyInstaller 静态收集。
- `check_log.py`：版本轮转、检查级去重、日志与旁车文件写入。调用方显式传入 cache。
- `snapshot.py`：把调用方传入的 cache 转成 JSON 安全快照，不读取全局 cache。
- `repair.py`：十一条修复规则与执行器。调用方显式传入 cache；两条修复复用游戏既有函数，这些函数内部使用游戏全局 cache，是仅有的反向依赖：`repair_work_npc_set` 调用 `basement.update_work_people()`，`repair_overcrowded_dormitory_room` 调用 `Dormitory_System/common.py` 的宿舍占用、居住类型与选房函数。

分层判据：**面向玩家的输出属于游戏侧，面向开发者的落盘属于检查包侧。** 因此检查包不导入游戏 UI 层；可在包目录执行 `rg 'Script[.]UI' --glob '*.py' .` 验证应为零命中。

状态语义按层区分：检查层只读、同一状态可重复计算；日志层刻意有记忆；修复层会写 cache。整个模块不可笼统称为“无状态”。

## 3. 公开接口

`static_check/__init__.py` 只公开三个函数和一个常量：

```python
__all__ = ["run_turn_check", "run_load_repair", "run_all_checks", "LOG_PATH"]
```

- `run_turn_check() -> bool`：调用方已确认总开关开启后调用。cache 未就绪时返回 `False`；否则运行全部检查并写入本版本尚未记录的检查。返回值只表示“本轮是否真的新增日志”，不表示“是否发现失败”。同一版本同一检查已记录后，即使仍失败也返回 `False`。
- `run_load_repair() -> List[dict]`：调用方已确认总开关开启后调用。返回全部实际修复记录；游戏侧可忽略，验证脚本据此断言。门面持有就绪守卫、惰性导入和唯一总兜底。惰性导入用于兜住 `repair.py` 导入期修复注册异常，避免阻断游戏启动。
- `run_all_checks() -> List[CheckFailure]`：只运行全部已注册检查并返回失败列表，不写日志。单条检查异常会转成 `CheckFailure(check_id, f"检查异常({check_name})", traceback, [])`，其余检查继续执行。
- `LOG_PATH`：从 `check_log` 再导出，供游戏侧警告文案引用。

内部接口不属于公开面：

- `check_log.write_error_log(failures, cache, context=None) -> bool`
- `check_log.write_repair_log(records, cache) -> None`
- `snapshot.build_snapshot(cache, involved_character_ids=None) -> dict`
- `snapshot.dump_snapshot_json(cache, involved_character_ids=None) -> str`
- `repair.apply_all_repairs(cache) -> List[dict]`

公开面为上述三函数加 `LOG_PATH`，不含 `update_context`、门面 `write_error_log`、警告绘制函数和总开关读取函数。玩家提示与开关判断由游戏侧挂钩完成，检查包不负责。

## 4. 检查函数规则

新增检查时，在 `checks/` 下新增模块或在既有领域模块中注册：

```python
@register_check("GROUPSEX-01", "群交参与人数一致性")
def check_group_sex_member_count() -> List[CheckFailure]:
    """
    参数:
        无
    返回值:
        List[CheckFailure]: 失败记录列表，空列表表示通过
    功能:
        校验群交场景中登记的参与人数与实际参与角色数量一致
    """
    cache = cache_control.cache
    failures = []
    return failures
```

必须遵守以下规则：

1. 检查函数一律无参，只读不写。**用到 `cache` 的检查函数**，函数体首个执行语句取 `cache = cache_control.cache`；不读取 `cache` 的检查函数不取该行——统一方言约束的是“取的位置”，不是“是否要取”。**不得把 288 条检查参数化传 cache**：进程内只有一个 Cache 实例，没有第二实现可注入；形式参数会制造“能传入但检查实际不一定使用”的说谎接口，并带来约 700 行机械改动。
2. 禁止模块级 `cache = cache_control.cache` 别名。全局 cache 在 `game.py` 启动后才赋值，并且新周目流程会重新绑定；模块级别名会永久持有旧对象。
3. 框架层采取相反规则：除门面 `run_turn_check`、`run_load_repair` 两处外，`check_log.py`、`snapshot.py`、`repair.py` 不得读取 `cache_control.cache`，必须显式接收 cache。
4. `make_failure` 的前两个参数必须与 `@register_check(check_id, check_name)` 逐字一致，以装饰器为准。
5. `check_id` 全局唯一。重复 id 会在该模块导入时抛 `ValueError`，因此该模块剩余检查不会注册；其他模块由逐模块导入隔离，不受影响。日志条目头会写出实际注册数，便于发现残缺注册表。
6. 检查不得修改状态，也不得调用会写状态的正式前提函数。已知写路径包括异常位掩码升级、指令过滤缺键补值和助理跟随 `setdefault`。
7. 每条检查文档须说明健康存档为何恒不命中。无法说明时不得注册。
8. 注册表、配置表、时钟和静态集合保持现有直接读取方式，不为不存在的第二实现新增注入层。

## 6. 日志契约

三条路径均相对于**游戏进程工作目录**，与 `error.log` 的约定一致：

- `static_check_error.log`
- `static_check_error.log.old`
- `static_check_seen.json`

一个日志文件只服务一个游戏版本。版本变化或首行损坏时，当前日志轮转为 `.old`，再写新版本头。轮转失败时本轮按“尽力写入”降级，下次写入仍会重试；任何异常不向游戏传播。

失败和修复条目公共头部为：

```text
================================================================================
[静态检查] 现实时间: <ISO> | 游戏时间: <game_time> | 周目: <game_round> | 已注册检查项: <实际数量>
最近输入(input_cache 末尾10条): ...
最近行为指令(pl_pre_behavior_instruce, id+名称): ...
```

只有调用方显式传入非空 `context` 时，才追加 `上下文包(context packet)` 行；门面不传 context，因此日志中没有恒空的 `{}` 行。

去重统一称为**检查级去重**：同一 `check_id` 每个游戏版本只详写首个失败实例。已见集合存入旁车文件，跨进程生效。因此 `run_turn_check()` 返回 `True` 至多每版本每检查一次；重复失败不写日志，也不重复提示玩家。禁止使用 message 参与去重，因为动态数值会使去重失效。

日志超过 50MB 后，本进程停止新增条目，只写一次说明行。修复记录不参与检查级去重，每次实际修复都留痕。

`check_log` 有三项相互关联的进程运行态：`_seen_check_ids`、`_log_cap_notice_written`、`LOG_PATH`/`OLD_LOG_PATH`/`SEEN_STATE_PATH` 路径常量组。同进程重复验证时必须重置前两个模块变量，并成组改向三个路径常量；只改一个路径会受到旧状态污染。门面 `static_check/__init__.py` 的 `LOG_PATH` 是从 `check_log` 按值再导出的独立名字：改向 `check_log.LOG_PATH` 后，已导入的 `static_check.LOG_PATH` 仍指向旧值，须同步改写或改用 `check_log.LOG_PATH` 读取。

## 7. 快照规则

`snapshot.build_snapshot(cache, ids)` 使用调用方传入的 cache。传入涉事角色 id 时，`character_data` 只转储涉事角色与玩家，最多 30 人；其余涉事角色只记 id。`scene_data` 只保留有角色的场景。

排除静态配置与渲染缓存字段，包括 `map_data`、`npc_tem_data`、`random_npc_list`、`recipe_data`、天文表、`wframe_mouse`、`cmd_data`、长流水字段，以及 `web_`、`current_`、`text_` 前缀字段。`rhodes_island.medical_patients_today` 用占位文本替代。

转换遇到循环引用、超过 15 层或对象不可序列化时使用 `repr` 兜底，不让快照异常逃出日志层。

## 8. 游戏挂钩与频率

每次主场景面板准备等待输入前执行一次，**包括纯 UI 重绘造成的重复迭代**。三个挂点直接写在游戏本体里，形式相同：先读开关，开关打开时才在 `if` 内部导入本包并调用接口，因此默认关闭时本包不会被导入，零开销。

- Tk：`in_scene_panel.py` 主场景 `askfor_all(ask_list)` 之前调用 `run_turn_check()`；返回 True（本轮新增日志）时用 `io_init.era_print(..., "warning")` 提示玩家提交日志。
- Web：`in_scene_panel_web.py` 取得 `ask_list` 之后、`askfor_all` 之前，同样调用与提示。
- 读档：`save_handle.input_load_save` 末尾，存档已写入 cache 之后调用 `run_load_repair()`。

三处调用都不套 try/except：本包两个入口自带总兜底（第 9 节），调用方无需处理异常。

用完整迁移后的真实 `save/1`（354 个角色）实测一次 `run_all_checks()` 为 **161.4ms**；最小 60 角色构造状态实测为 20.6ms（2026-08-23 测得）。纯 UI 重绘会重复计算，但检查级去重保证日志和玩家提示不增长。若检查集增长，应继续把共享配置查表移到角色循环外，而不是降低挂钩频率。

## 9. 异常边界

异常边界只有三层，各自负责一件事：

1. `run_all_checks()` 逐检查隔离，将单条检查异常转换为失败记录。
2. `run_turn_check()` 与 `run_load_repair()` 各有一个入口总兜底，覆盖就绪守卫、惰性导入和内部调用。
3. `write_self_error_log(exc)` 是日志终点，自身在任何情况下都不抛出。

修复执行器只做逐修复隔离，不重复总兜底；日志调用点不套第二层 `try/except`（该层无效）。调用方无需捕获静态检查异常。

## 10. 总开关、debug 与验收

总开关是 `base_setting` 的 cid 14“是否开启游戏状态自检”，**默认关闭**（cid 13 已被“生殖方式开关”占用）。三个游戏挂钩必须先执行：

```python
cache.all_system_setting.base_setting.get(14, 0)
```

必须使用 `.get` 并带默认值 0，不能使用 `[14]`。旧存档设置补齐只在键数量变化时逐键修复，存在“键数相同但键集合不同”的版本演进情况；裸下标可能抛 `KeyError`，直接违反绝不阻断约束。

检查与修复同开同关。开关由游戏侧挂钩判断，检查包门面被调用即执行；包内另有 cache 未初始化、角色表为空、玩家不存在三道机制就绪守卫。

`debug_mode` 的豁免故意不对称：检查仍运行，各检查按自身语义决定是否跳过；载入修复整体跳过，避免把 debug 面板有意制造的状态自动改回。

288 条 checks 不参数化传 cache：进程内只有一个 Cache 实例，参数化提供不了真实替换能力，只会扩大接口和机械改动。框架层显式传 cache 则是为了收敛依赖。两条规则不得混用。

最低验收要求：

1. 先完成 `normal_config.init_normal_config()` 与 `game_config.init()` 再导入门面，注册表为 288 条、修复表为 11 条、检查异常为 0。裸导入环境（跳过上述初始化）下部分检查模块会因配置缺失而导入失败；断言288条必须带上初始化前置，不能用裸导入的注册数代替完整验收。
2. 用完整迁移的真实存档复跑：既有检查除本轮明确调整的判定外，失败集合与修复数量不变；新增命中须逐条对照写入方判定；注册了修复的检查在修复后全部通过。
3. 日志格式的固定项：头部写出实际注册数、不输出空 context 行、版本轮转、检查级去重、50MB 上限；改动本系统不得动这些项。
4. 总开关关闭时，三个游戏挂钩零调用、零写入。
5. `rg "Script\.UI" --glob "*.py" .` 为零；框架层 `cache_control.cache` 读取只在门面两个入口中出现。
