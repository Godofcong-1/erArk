- 状态：**已实施**（2026-08-21，见 §11）

## 1. 目标

1. 让 `data/target/default/target.csv` 的 cid 成为**自解释的结构化编号**：从 cid 本身即可读出「属于哪个 type、属于哪条行为链、在链中第几步」。
2. 让 **cid 升序 == 物理行序 == AI 优先级顺序**，使优先级错误在文件里肉眼可见、并可被脚本拦截。
3. 为后续开发预留充足空号：新增一条行为链、或在既有链中插入一步，都不需要再动其他行的编号。
4. 提供配套 lint 脚本，把编号约定固化为可执行的检查，纳入日常开发流程。
5. 全程**不改变任何一条目标的实际优先级**，即重构前后 NPC 行为完全一致。

### 2.2 现行的隐含约定（无文档，靠惯例维持）

逐行分析后可以还原出三条从未写下来的规则：

1. **十位数 = 行为链**，个位数 = 链内步骤。例如 `5x` 是洗澡链：`51` 入口(type 11)、`52~57` 链身(type 12)、`58` 睡奸醒来入口(type 0)、`59` 收尾(type 12)。
2. **物理行序按行为链聚合**，同一条链的 type 0/11/12 行紧挨在一起。
3. **cid 全局升序恰好等于物理行序**（Plan 07 之前 163 行无一例外）。

### 2.3 Plan 07 暴露的三个结构性缺陷

Plan 07 需要新增 9 行（900~908），暴露出：

**缺陷一：链块容量耗尽。** 洗澡链 `51~59` 九个号全部用完，新增的助理洗澡链无号可用，只能跳到 `900`，语义上与 `5x` 块完全脱节。

**缺陷二：链聚合与优先级顺序不可兼得（根本矛盾）。** 助理洗澡的收尾行必须排在 **type 11 的最前面**（要抢在就寝入口 cid 23 之前），但它语义上属于洗澡链，应该待在 `5x` 块里 —— 而 `5x` 块在文件中位于睡觉块 `2x` 之后。

> 这不是“号段没留够”能解决的问题：**同一条行为链的不同步骤，在同一个 type 内可能需要处于完全不同的优先级位置。** 只要坚持「一条链 = 一个连续号段」，就必然与优先级排序冲突。现行编号只是一直没碰上这种情况而已。

**缺陷三：约定不可校验。** Plan 07 的插入使「cid 升序 == 行序」在 4 处被打破（900 在 21 前、901 在 51 前、908 在 52 前、902 在 58 前），但没有任何机制会报错。

### 2.5 构建器对空行与注释行的处理（已实测）

分区标记怎么写，取决于 CSV 解析器容忍什么。已实测 `csv.DictReader`（`buildconfig.py` 用的就是它）对两种分隔方式的行为：

| 写法 | DictReader 产出 | 后果 |
| --- | --- | --- |
| 空行 | **不产出任何行**（`DictReader.__next__` 内部 `while row == []` 主动跳过） | **安全**，现有文件已在用 |
| `# ── type 0 高优先度 ──` | `{'cid': '# ── type 0 高优先度 ──', 'state_machine_id': None, 'premise_id': None, 'type': None, 'remarks': None}` | **不可用**，见下 |

注释行会一路走到底并被写进 `Target` 表：

1. `buildconfig.py:172-174` 对 4 个 `None` 列各打印一次 `Error: 文件 ... 出现缺失行`，然后 `continue` 只跳过该列；
2. `cid` 列声明为 `int`，`int("# ── type 0 ...")` 抛异常，被 `buildconfig.py:186-187` 捕获并打印 `Error processing row`；
3. 行尾的 `config_data[type_text]["data"].append(row)`（`buildconfig.py:215`）**无条件执行**，垃圾行照样入表；
4. `game_config.py:1498` 随后会以 `type=None` 建出一个 `config_target_type_index[None]` 条目。

**结论：分区之间只能用空行分隔，不能写 `#` 注释行。** 分区标题改为在 §4.5 的说明文档里维护一张对照表；由于 cid 前两位即 type，文件内不写标题也不影响辨认。

`tools/csv_renumber.py` 已存在 `renumber_csv(file_path, start_value, start_line=6, column_index=0)`，默认 `start_line=6` 恰好跳过 `target.csv` 的 5 行表头。但它只能写**稠密递增**序列（`start, start+1, start+2…`），会摧毁号段语义，也不会同步 `effect.csv`、不产出新旧映射表。**本 Plan 不复用它**，另写专用脚本。

## 3. 设计决策

### 3.1 出发点：什么才是编号真正要表达的东西

运行时唯一依赖的是**物理行序**：`config_target_type_index[type]` 按 CSV 行序 `append`（`game_config.py:1499`），types 11/12/13 用 `get_first_only=True` 取第一个前提全通过的行（`handle_npc_ai.py:565`）。cid 本身**不参与任何运行时判定**，纯粹是标识符。

既然如此，编号的职责就只有一个：**让「物理行序 = 优先级」这件事在文件里显式可见、可校验。**

由 §2.3 缺陷二可知，「链聚合」与「优先级排序」二者不可兼得。既然优先级是运行时正确性、链聚合只是可读性，那就必须**优先服从优先级**。

### 3.2 推荐方案：`cid = type × 10000 + 组号 × 100 + 组内序号`

```
   1 1 0 2 0 5
   └┬┘ └┬┘ └┬┘
    │   │   └── 组内序号，按 5 递增（0,5,10,…,95），中间 4 个位置留给插队
    │   └────── 组号 01~99，00 预留给“必须插到该 type 最前面”的紧急情况
    └────────── type（两位，取值同 Target_Type.csv）
```

- 校验规则一句话：**`cid // 10000 == type`**。
- type 0 的 cid 是 3~4 位（如 `100`），type 43 是 6 位（如 `430110`），长度不齐但规则统一。
- **cid `0` 永久保留给 CSV 第 4 行的占位行**，因此组号从 `01` 起、组 `00` 若启用则序号从 `5` 起。

**「组」的定义 = 同一 type 内、物理行序上连续的同一条行为链。** 注意这**不等于**「一条行为链一个组」：同一条链若在同一 type 内被拆到不同优先级位置，就占用多个组。例如洗澡链在 type 11 里占两个组：

- `110100` 组 01 —— 洗澡收尾（原 900，必须最高优先级）
- `110400` `110405` 组 04 —— 洗澡入口（原 901、51，排在睡觉/吃饭之后）

这正是对 §2.3 缺陷二的正面回应：**放弃「一条链一个号段」的幻想，改为「一个优先级段一个组」，链的归属靠组名与备注表达。**

### 3.3 物理行序同步重排为 type 分区

新编号要求 `cid 升序 == 行序`，因此文件布局也要从「按行为链聚合」改为「按 type 分区，区内按优先级」：

```csv
100,503,...,0,...          ← type 0 区，从 100 起
105,504,...,0,...
                            ← 空行分隔（构建器会跳过）
10100,0,...,1,...          ← type 1 区，从 10100 起
10105,1,...,1,...

110100,88,...,11,...       ← type 11 区，从 110100 起
110200,78,...,11,...
```

分区之间只用空行，不写标题（§2.5 已实测注释行不可用）。cid 的前两位就是 type，因此不写标题也能一眼分辨分区边界。

**取舍说明**：这样一条完整行为链（如洗澡）的行会散布在 type 0/11/12 三个分区里，读链要跨区跳转，可读性有损失。但换来的是：

- 每个 type 分区内，从上到下就是优先级从高到低，**一眼可查**；
- 任何插错位置的行都会造成 cid 逆序，被 lint 直接拦下；
- 与运行时的实际扫描方式（按 type 分别扫描）完全对应。

链的可读性通过三个手段补偿：cid 中的组号、`remarks` 列已有的中文描述，以及 §4.5 要写入说明文档的「行为链 → (type, 组) 对照表」。

### 3.4 备选方案与否决理由

| 方案 | 描述 | 否决理由 |
| --- | --- | --- |
| **B. 保留链聚合布局，仅重编号** | 文件仍按行为链分块，cid 编码 type+组，只强制「同 type 内 cid 升序」 | 由 §2.3 缺陷二，需要高优先级的链尾步骤**本来就必须物理移出自己的链块**，链聚合已被现实打破。保留它等于保留一个做不到的承诺，且优先级关系在文件里依然不可见。 |
| **C. 稠密顺序编号（1,2,3…）** | 直接用 `tools/csv_renumber.py` 重排 | 任何插入都要重编后续全部行，且 cid 不携带任何语义，退步。 |
| **D. 不动编号，只加 lint** | 仅补「同 type 内 cid 升序」检查 | 当前 4 处违规无法修复（`900` 语义上就不该是 900），且链块容量耗尽的问题原样保留。 |

### 3.5 预留规则（本 Plan 的主要交付物之一）

给后续开发的操作指引，需写入 `.github/prompts/数据处理工作流/`：

**要在既有链的某一步之后插一行** → 用相邻两个组内序号的中间值。
例：在 `120305` 和 `120310` 之间插 → `120307`。

**要给既有链追加一步** → 用该组的下一个 5 的倍数。
例：洗澡链 type 12 组 03 现用到 `120360`，下一步用 `120365`。组内还有 `120365~120395` 共 7 个主位。

**要新增一条完整行为链** → 在每个涉及的 type 分区里各开一个新组，组号取该 type 尚未使用的下一个值。
例：新链在 type 11 需要入口、type 12 需要 4 步 →
type 11 现用到组 08，取组 09 → `110900`；
type 12 现用到组 07，取组 08 → `120800/120805/120810/120815`。
物理位置按该链应有的优先级放入对应 type 分区。

**要插入一条优先级高于现有全部的行** → 用组 00，序号从 5 起（如 type 11 → `110005`）。

**容量核算**：每 type 99 个组（当前最多用到 8 个），每组 20 个主位、100 个可用位置（当前最大组 13 行）。按现有增速，十年内不会耗尽。

## 4. 详细改动步骤

### 4.1 新增迁移脚本 `tools/target_cid_migrate.py`

一次性脚本，职责：

1. 读 `data/target/default/target.csv`，解析出 `(物理行号, cid, state_machine_id, premise_id, type, remarks)`。
2. 按内置的「旧 cid 区间 → 行为链名」表给每行打上链名（表见 §3.6，需完整列出 27 个区间）。
3. 对每个 type，按**物理行序**扫描，链名发生变化就递增组号，为每行算出新 cid = `type*10000 + 组*100 + 组内序号*5`。
4. 按新 cid 升序重排全部行，按 type 分区输出，**分区之间只插入空行**（不能写 `#` 注释行，理由见 §2.5）。
5. 同步改写 `data/target/default/effect.csv` 的 `target_id`（`6` → `10115`）。
6. 输出 `tools/output/target_cid_mapping.csv`（`old_cid,new_cid,type,group,chain,remark`）留档。
7. 自检：R1~R5 全通过才写盘（规则见 §4.2）。

脚本的核心逻辑已验证可行（见 §6.1）。

### 4.2 新增常驻校验脚本 `tools/lint_target_csv.py`

固化编号约定，供日常开发与提交前调用：

| 规则 | 内容 | 违规后果 |
| --- | --- | --- |
| R1 | cid 全表唯一 | 构建时后者覆盖前者，静默丢行 |
| R2 | 同一 type 内，cid 升序 == 物理行序 | **优先级错乱**（本次事故的根因） |
| R3 | 全局 cid 升序 == 物理行序 | 可读性破坏 |
| R4 | `cid // 10000 == type` | 编号脱离体系 |
| R5 | `premise_id` 中每个前提名都能在 `constant.handle_premise_data` 中解析 | 该行**永远不会被选中**（cid 32 曾因此失效） |
| R6 | `state_machine_id` 存在于 `constant.handle_state_machine_data` | 选中后崩溃 |

## 7. 风险与注意事项

1. ~~注释行能否被构建器接受~~ —— **已实测排除**：只能用空行分隔（§2.5）。迁移脚本若误写注释行，会静默污染 `Target` 表，因此 §4.2 的 lint 需额外覆盖「数据区不得出现非法行」。
2. **`data.json` 的 git diff 很大**，建议编号重构单独成一个提交，不要与逻辑改动混在一起，方便日后 review 与回滚。
3. **`random.choice` 的 tie-break 会变**：`handle_npc_ai.py:577` 对一个 cid 字符串 `set` 做随机选取，set 迭代序由哈希决定。重编号后同权重目标间的选中顺序会变化。功能上无差别（本来就是随机），但**带固定随机种子的复现实验无法与旧编号对齐**。
4. **在途分支冲突**：本重构触及 `target.csv` 全部 163 行，任何同时修改该文件的分支都会产生大面积冲突。应挑一个没有并行改动的时间窗口执行，或要求其他分支先合入。
5. **组的划分带有主观性**：§3.6 的 27 个行为链区间是人工归纳的。若某处归纳错误，只影响组号美观，不影响正确性（R2/R5' 仍成立）。
6. **Mod 目录**：若将来 `data/target/` 下出现第二个目录，它有独立的 cid 前缀命名空间，应各自遵循同一套编号规则，但号段互不冲突、无需协调。
7. **`effect.csv` 目前是死数据**：其消费方 `config_effect_target_data` 在 `handle_npc_ai.py:533-552` 被整段注释。仍需同步更新 `target_id`，否则将来该功能启用时会指向错误的目标。
