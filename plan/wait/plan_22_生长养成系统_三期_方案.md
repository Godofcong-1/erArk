## 1. 本期目标

取自总纲 §1 的第 9 条，并纳入口径 25、26、36：

1. 全阶段（婴儿→少女）的养成事件由玩家在「处理公务」中决断，选择影响性格倾向与养成走向
2. 事件表支持批量增删改查，新增一条事件只需往 CSV 追加一行
3. 孩子之间的互动（兄弟姐妹、同班同学）通过关系数值 + 养成事件呈现
4. 成年时在大礼堂举行毕业典礼与成年纪念事件

**验收标准**：能在处理公务中逐条处理养成事件，选项影响性格倾向；事件表可批量增删改查；成年时触发毕业典礼。

## 2. 本期专属现状调查

全局现状调查见**总纲 §2**，本节只补本期最需要盯住的三处。

### 2.1 既有事件系统的形态

`data/event/event.json`，每条含 `uid / adv_id / behavior_id / start / type / text / premise / effect`，由 `Script/Design/event.py` 处理，**按 `behavior_id` + `premise` 触发**。ArkEditor 已支持事件的增删改查。

⚠️ **触发模型不同**：既有事件是"做了某个行为时触发"，养成事件是"孩子的成长状态满足条件时，按周期/随机入队"。所以本期复用它的**数据形态与编译链**，但**另起一套触发逻辑**（§3.7）。

### 2.2 处理公务的入口

指令 2001 `official_work`（`InstructConfig.csv:60`，`Script/Core/constant/Behavior.py:140 OFFICIAL_WORK`），前提 `IN_DR_OFFICE｜HAVE_OFFICE_WORK_NEED_TO_DO`，效果在 `constant_effect.py:433` 按学识与办公室等级消耗工作量。

养成事件挂在这条指令上：玩家在博士办公室处理公务时，队列里的养成事件逐条弹出决断。

### 2.3 事件幂等的既有做法

一期已在 `CHILD_GROWTH` 里建好 `event_history`（键 str 事件 uid，值 dict 含 `time` 与 `choice`），本期开始写入。⚠️ 一次性事件必须查 `event_history` 防重复触发——这是本期唯一的幂等要求，成长阶段跃迁类事件靠素质变化天然幂等（如成年事件的守卫是素质 103→104），但"第一次上课""第一次考砸"这类必须靠 uid 记录。

## 3. 设计决策

### 3.7 养成事件独立子系统，归入处理公务

**载体**：复用既有事件系统的数据形态（`data/event/event.json` 的 uid / premise / effect 结构），但**独立成一套养成事件配置**。理由见 §2.1：既有事件按 `behavior_id` 触发，养成事件按"孩子的成长状态 + 随机/周期"触发，触发模型不同，硬塞进去会污染既有事件的判定路径。

**数据流**（与既有事件一致，可复用 ArkEditor 与 buildconfig 链）：

```
data/growth_event/*.csv  →  buildconfig  →  data/Growth_Event.json  →  运行时 config
```

**触发与呈现**：

1. 每日结算时按前提筛出可触发的养成事件，写入待处理队列
2. 玩家在博士办公室「处理公务」（指令 2001）时，队列中的养成事件逐条弹出
3. 每条事件给 2~4 个选项，玩家决断
4. 选项的 effect 影响：性格倾向（`personality_point`）、能力经验、好感信赖、后续事件解锁

**入队节流**（口径 32）：每日最多入队 **2 条**（`growth_event_handle.GROWTH_EVENT_DAILY_MAX`），未处理的留在队列到下次公务。⚠️ 这条不是可选优化——多孩时若不节流，一次公务会涌出十几条事件，玩家会直接失去判断意愿。

⚠️ 节流是**全局**上限不是每孩上限：实现上先把所有孩子的候选汇成一个池子再加权抽 2 条，而不是每个孩子各抽一条——后者等于把上限变成「孩子数 × 1」，节流就没了。

另设**队列硬上限 12 条**（`GROWTH_EVENT_QUEUE_MAX`）：玩家可以很久不处理公务，不封顶的话回来时会面对一长串陈年旧事。满了就不再入队（丢弃新事件而非挤掉旧事件——旧的至少还有上下文）。

**结果尺度**（口径 33）：选错会导致性格偏向不如预期、好感小幅下降，但**不掉能力、不造成不可逆损失**。养成事件是塑造方向的，不是惩罚失误的。

**选项前提**（口径 34）：复用既有前提系统与 CVP token，不满足时**置灰并标明原因**（如"好感不足"），而不是隐藏——让玩家看见"这里本来有更好的选择，但我没养到"。

⚠️ 原因文案由作者在 CSV 的 `option_N_reason` 列手写，不从前提反推：前提系统里没有任何一张"前提 → 人话说明"的表，`CVP_A1_F_GE_200` 这种 token 自动翻译出来的只会是天书。

**批量增删改查**（口径 12、16）：事件表按阶段分文件（`婴儿.csv` / `幼女.csv` / `萝莉.csv` / `通用.csv`），每行一条事件，列含 `cid / 阶段 / 前提 / 文本 / 选项1~4 / 各选项effect`。批量生成时只需往 CSV 追加行，与既有口上 CSV 的工作方式一致。

⚠️ ArkEditor **不扩展**（实施时已确认）：它的数据模型硬绑 `behavior_id` + `adv_id` + 单条 premise/effect/text，而养成事件一行带四个各自独立的选项块，要另起一整套 grid 布局。走方案原定的退路——直接手写 CSV，事件表是扁平的一行一事件结构，可行，只是不如编辑器方便。只把两个新前提同步进了 `tools/ArkEditor/csv/Premise.csv`，让口上作者在编辑器里也能选到它们。

### 3.7.1 养成数值的读写通道：CVP / CVE 的 `Growth` 子类型

性格倾向与照料值既要能当**事件前提**读、又要能当**选项结算**写，而它们都不在 CVP/CVE 已有的 A能力/T素质/F好感 之类里。做法是给这两套 token 各加一个 `Growth` 子类型，而不是另造一套养成专用 token：

```
CVP_A1_Growth|<编号>_<运算>_<值>     前提：读养成数值
CVE_A1_Growth|<编号>_<G/L/E>_<值>    结算：写养成数值（值可带小数）
```

| 编号 | 含义 | 可写 |
| --- | --- | --- |
| 0 | 累计听课节数 | 否 |
| 1 | 累计缺课节数 | 否 |
| 2 | 出勤率百分比（0~100，一节没上过算100） | 否 |
| 10~13 | 四对性格倾向（10+性格对编号），正数偏前者 | 是 |
| 20 | 照料累积 `care_point` | 是 |
| 21 | 胎教累积 `prenatal_point` | 否 |
| 22 | 已触发的养成事件条数 | 否 |

统一从 `growth_handle.get_growth_value()` / `change_growth_value()` 走，前提、事件、面板共用一个口，免得同一个「出勤率」在三处各算各的。

⚠️ **出勤数、胎教值只读不写**：出勤由上课结算记账、胎教由妊娠期写入，让事件改它们会让面板上的「听课 N 节」变成一个谁都对不上的数（口径 33 也不允许事件动能力）。

⚠️ **`Growth` 与既有的 `Gift`、攻略程度共用首字母 G**，三者在同一个 `elif [1][0] == "G"` 分支里，`Growth` 必须判在最前，且攻略程度那段「不过 0 夹逼」要显式放过 `Growth`——养成数值是可正可负的普通数值，套上夹逼后负的性格倾向永远判不出来。

### 3.25 孩子之间的互动：关系数值 + 养成事件

口径 25、36 的落地方式：

| 层 | 做法 |
| --- | --- |
| 数据 | 复用既有 `relationship` 结构（`game_type.py:366~370` 的 `father_id` / `mother_id` / `child_id_list`）建立兄弟姐妹关系；同班同学关系由课表反查（同一格子的学生互为同学） |
| 呈现 | 全部通过养成事件呈现——"薇薇安和妹妹为了一个玩具吵架了""两个孩子在实践课上互相帮忙" |
| 结算 | 事件选项影响两个孩子的好感与各自的性格倾向 |

⚠️ **不做 NPC 之间的自主行为目标链**（口径 36）。让两个孩子在场景里自主互动需要给 NPC AI 加一整套"以另一个 NPC 为目标"的行为选择，影响面远超本计划。用事件呈现，成本低且叙事密度更高。

**互动对象怎么落到结算上**：队列元素带一个 `partner_id`，入队时按事件前提挑好（含 `self_have_sibling_child` 就从兄弟姐妹里挑，含 `self_have_classmate` 就从同学里挑，都没有则为 0 即博士）。判前提与跑结算时**临时把孩子的 `target_character_id` 指向 `partner_id`**，于是 token 里的 `A2` 天然指向本次事件的互动对象，判完/结算完立刻还原。

⚠️ 这样做才不用给 CVE 再造一个"第三方角色"的主体类型——`A1` 是孩子、`A2` 是互动对象，与全游戏其他地方的语义完全一致。⚠️ 还原必须放在 `finally` 里：`target_character_id` 是行为循环在实时读的字段，留着不还会让孩子下一拍去找错人。

**两个新前提**（`constant_promise.Premise`）：

| 前提 | 判据 |
| --- | --- |
| `self_have_sibling_child` | 同为孩子、且**有效**双亲 id 有一个相同。⚠️ 双亲未登记时是 -1，不排除掉的话两个都没登记的角色会互相认成兄弟姐妹——世界设定的「萝莉化」会给一大批干员挂上萝莉素质，正好撞进这个洞 |
| `self_have_classmate` | 个人课表里有 (星期, 节次, 课型, 目标) 完全相同的格子。⚠️ 由课表现算而不落成字段：课表一改同学关系就跟着变，存字段反而多一处同步点 |

### 3.26 毕业典礼与成年纪念：做成事件，不做指令

口径 26、44。

| 事件 | 触发条件 | 舞台 |
| --- | --- | --- |
| 毕业典礼（uid `通用1`） | 成年结算时（素质 103→104，二期方案 §3.8 的 `check_grow_to_girl`）插到队列**最前**，玩家下次处理公务时举行 | 大礼堂（一期方案 §3.10 新建的 `Auditorium`） |
| 成年纪念（uid `通用2`） | 紧排在毕业典礼之后 | 同上 |

⚠️ **不做成指令行为**（口径 44）：毕业典礼是一次性的叙事节点，做成玩家指令意味着要配行为、时长、口上、前提一整套，而它一辈子只触发一次。事件系统的一次性叙事正是为此而生。

⚠️ **不在成年结算当场弹出，而是插队首**：`check_grow_to_girl` 跑在 NPC 的行为循环里，当场弹一个要玩家做多选的界面会把循环卡在中间。改为插队首 + 在成年结算的文本里加一行"大礼堂已为她备好了毕业典礼，等你下次处理公务时定夺"，既保住了叙事节点的分量（它一定排在一堆日常事件前面），又不打断循环。

⚠️ 这两条的幂等**不靠 `event_history`**，靠成年结算本身的守卫（素质 103→104，一个孩子只会经过一次）。它们的 `stage` 写 104，所以日常入队路径也会给"已成年但还没办过典礼"的女儿补派——旧存档里已经长大的女儿因此能追认到一次典礼，这是有意保留的。

⚠️ 大礼堂在一期只做公开课（口径 15），**它的养成事件舞台功能在本期才启用**——这是一期与三期的接口。

## 4. 数据结构设计

本期**不新增角色字段**——`CHILD_GROWTH.event_history` 与 `personality_point` 已在一期建好并做了存档回填，定义见**一期方案 §4.1**。

本期新增的是全局待处理队列：

```python
        self.growth_event_queue: list = []
        """ 待玩家在公务中处理的养成事件队列（Plan 22 三期）
            元素dict:{"uid": 事件uid str, "chara_id": 孩子角色id int,
                      "partner_id": 互动对象角色id int（无则0）, "add_time": datetime}
            每日最多入队2条（口径32）；处理后出队并写入该孩子的 event_history """
```

挂 `Rhodes_Island`（`game_type.py:1270`），旧档在 `save_handle.py:556` 附近回填为 `[]`。

⚠️ `partner_id` 是方案定稿后补进来的一列：孩子间互动事件的结算要落到两个人身上，见 §3.25。

⚠️ **这是本期唯一的存档结构改动**。一期没有预建它，因为队列的元素结构直到本期设计定型才确定；它是 list 不是 dict，回填只需 `hasattr` + `= []`，风险很低。

### 4.1 养成事件表的列结构

`data/growth_event/{婴儿,幼女,萝莉,通用}.csv`：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `cid` | str | 事件 uid，文件名自动加前缀（照口上 CSV 的 `buildconfig.py` 机制），如 `萝莉1` |
| `stage` | int | 适用阶段素质 id（**0 = 全部未成年阶段 101~103** / 101 婴儿 / 102 幼女 / 103 萝莉 / 104 少女） |
| `once` | int | 是否一次性（1 则查 `event_history` 防重复） |
| `weight` | int | 入队权重，与前提算出的权重相乘 |
| `premise` | str | 触发前提，`&` 连接，复用既有前提与 CVP token |
| `text` | str | 事件正文（可用口上代码，`talk.code_text_to_draw_text` 转换） |
| `option_1~4` | str | 选项文本，空则该选项不存在 |
| `option_1~4_premise` | str | 选项前提，不满足则置灰 |
| `option_1~4_reason` | str | 前提不满足时显示的原因，作者手写（见 §3.7） |
| `option_1~4_tip` | str | 后果提示，只写方向不写数值（见 §5.1） |
| `option_1~4_effect` | str | 选项结算，`&` 连接，CVE token 或 `Behavior_Effect` 的纯数字结算id |

⚠️ **`stage = 0` 不含已成年的 104**：不这样切的话，女儿成年后会一直被派到"生日""换季"这类为孩子写的日常事件。成年后只接 `stage` 明确写 104 的事件（毕业典礼与成年纪念）。

⚠️ **空着的列在构建时会被整列删掉**，所以运行时一律用 `dict.get()` 取值、不能用 config 对象取属性——取不到就是"这条事件没有这个选项"。运行时表因此存的是原始 dict（照 `config_cook_question` 的做法），不是 `config_def` 对象。

## 5. 界面与信息架构

### 5.1 公务中的事件弹出

在既有的处理公务流程里插入养成事件段：

```
【养成事件】薇薇安 · 萝莉期第 38 天
--------------------------------------------------
  薇薇安拿着这学期的成绩单站在你面前，学识拿了个 C，
  但战斗课的成绩几乎垫底。她低着头，手指绞着衣角。

  1. 摸摸头，说"尽力就好"        （好感＋，倾向：脆弱）
  2. 指出她战斗课确实没认真上    （好感小降，倾向：坚强）
  3. 提出以后陪她一起练          （好感＋＋，倾向：勤劳）
   ○ 让她自己想办法（她对你的信赖还不够）   ← 灰字，不可点
--------------------------------------------------
```

可点的选项是带序号的按钮，置灰的选项画成 `deep_gray` 的普通文本、序号让位给 `○`——不占按钮序号，玩家一眼能分清哪些是现在能选的。

⚠️ 一条事件的选项**全部不可选**时不弹按钮、直接跳过（画一行"这件事已经不需要你来决定了"），否则玩家会被卡在一条谁也点不了的事件上出不去。

⚠️ **选项的后果提示要写出来**（"倾向：坚强"），但**不写具体数值**。玩家需要知道选择的方向，不需要知道加了几点——后者会让养成变成算数题。

### 5.2 养成事件履历

在一期的养成总览面板（一期方案 §5.4）里加一栏「养成履历」，按时间正序列出该孩子已触发的事件与当时的选择，读 `event_history`。最多列最近 8 条，更早的折成一行"（更早的 N 条已略去）"——养到成年会攒下几十条，全列出来会把总览面板顶爆。

同时在总览的「待处理」栏加一条"有 N 件关于她的事等你在博士办公室「处理公务」时决断"。⚠️ 不提示的话玩家根本不知道要去哪里处理，事件会一直躺在队列里。

## 6. 与其他期的接口

| 接口 | 依赖方向 | 说明 |
